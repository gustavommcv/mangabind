# Full audit — October 2026

- Date: 2026-10-07
- Scope: conformance with [clig.dev](https://clig.dev/) and with the project's own ADRs, correctness of grouping and parsing, behaviour on hostile or odd input, the machine contract (protocol v1), supply chain and release, and documentation and tests against the code.
- Snapshot: 30 commits, 14 ADRs, `main` at `916f404` (PR #6), release `v0.6.1` (published 2026-10-05). About 2,170 lines of Go and 2,440 lines of tests, no third-party dependencies.
- Method: a read of every Go file in `cmd/` and `internal/`, of `.github/`, `.goreleaser.yml`, `.golangci.yml`, the install scripts, the README, CONTRIBUTING, ADR 0009 and ADR 0011, and the protocol document. Then the built binary was run against fixtures made for this audit (about 40 invocations, listed under each finding), and these tools were run: `go vet`, `go test -race -cover`, `staticcheck`, `golangci-lint` v2.14.0 (the repository's own config, then a wider set), `govulncheck` (source mode, under Go 1.23.12 as CI builds it, and binary mode on the published `v0.6.1` archive), and 25 seconds of native fuzzing each on the parser registry and on `naturalsort.Less`. Everything was run on Linux. The fixtures and scripts were not kept; the commands are in the findings.

This is a report, not a plan. It names what is wrong, where, and what the direction is; deciding what becomes a pull request, and in what order, is a separate step. Nothing in the repository was changed except this file.

**How findings are classified.** *Defect*: the behaviour contradicts the project's own ADR, README or protocol document. *Gap*: a clig.dev item that the ADRs neither adopted nor declined. *Reconsider*: something an ADR declined or accepted whose premise has since changed. Priority is High, Medium or Low; effort is S (a few lines and a test), M (one focused pull request) or L (a design question first).

**What was not read or run.** ADRs 0002–0008, 0010 and 0012–0014 were not read in full (only their entries in the index and the places the code cites them). Windows and macOS behaviour was not run: reserved Windows names (`NUL`, `CON`), case-insensitive collisions and `\` in zip entry names were reasoned about, not tried. A real full disk was simulated with `ulimit -f`, not produced. The install scripts were read, not executed. `testdata/` was not reviewed. No real manga collection was used; the fixtures are synthetic.

## What is already working well

- **The output is deterministic.** Two runs over the same input produced byte-identical `.cbz` files (compared by SHA-256), because no timestamps are written. That is worth keeping on purpose. Its only cost is cosmetic: the zip entries carry a zero DOS date, which `unzip -l` prints as `1980-00-00` (Python's `zipfile` reads and extracts the archive without complaint).
- **Static analysis is clean.** `go vet`, `gofmt -l`, `staticcheck` and the repository's own `golangci-lint` configuration report nothing. `go test -race ./...` passes in all six packages (coverage: `cbz` 90.0%, `grouper` 96.7%, `metadata` 97.6%, `naturalsort` 90.9%, `parser` 86.4%, `scanner` 94.3%, `cmd/mangabind` 77.8%). Fuzzing the parser registry (149,000 inputs) and `naturalsort.Less` (715,000 inputs, checking that two strings are never each less than the other) found nothing. All name parsers use Go's `regexp` (RE2), so a hostile folder name cannot make them run in more than linear time.
- **The machine contract matches its document.** Every issue code in the source is in the table in `docs/machine-protocol-v1.md`, and every code in the table is emitted by the source (`empty_chapter` is set by reassigning the code, which a grep for `issue(` does not show). With `-json`, stdout was exactly one JSON line and stderr was empty. The `-progress-json` events matched the document field for field (13 events for a two-volume run, counters resetting per manga, `completed` only after the archive is closed). `-progress-json` without `-json` is refused with exit 2.
- **The link policy of ADR 0014 works.** A page that is a link to `/etc/hostname` is skipped with a warning naming it, and does not reach the volume.
- **Per-manga failure isolation in `-batch` works.** A manga with an unreadable page does not stop the others, and the exit code is 1 with a message naming the manga.
- **Exit codes are consistent** (0 success, 1 runtime failure, 2 usage) across human and machine mode, and a failing `-json` run still prints a parseable report.
- **The distribution is as small as it can be.** One static binary (`CGO_ENABLED=0`), six archives plus `checksums.txt` per release, an uninstall section in the README, no network access anywhere in the code, no telemetry.

## Findings — behaviour and safety

### 1. `-dry-run` and every flag after the first positional argument are silently ignored

**Class:** defect (ADR 0009: "dry-run performs the real plan without writing"; clig.dev: flags should be accepted in any order, and an unexpected argument should be refused). **Priority:** High. **Effort:** S.

**Where:** `cmd/mangabind/main.go:202` (`fs.Parse(args)`); `fs.Args()` is never read anywhere in the file. Go's `flag` package stops parsing at the first non-flag argument.

**Evidence:**

```
$ mangabind -input Manga extra -dry-run -output out2
mangabind: no -output given, writing to Manga (mangabind)
wrote Manga (mangabind)/Manga - Vol.01.cbz (5 pages)
wrote Manga (mangabind)/Manga - Vol.02.cbz (2 pages)
exit=0          # out2 does not exist; two real files were written
```

`extra` was taken as a stray argument, and `-dry-run -output out2` after it were never parsed, with no message. The same thing happens when a shell expands a glob or an unquoted name containing a space into two words after `-input`: the first word becomes the input, the second ends the flags, and whatever follows is dropped.

**Why it matters:** the one flag whose job is to guarantee that nothing is written can be dropped without a word, and the run that follows overwrites any file of the same name in the default output folder.

**Direction:** after `Parse`, if `fs.NArg() > 0`, refuse with exit 2 and one line (`unexpected argument "extra"; if it is part of a path with spaces, quote the path`), in machine mode as an `invalid_arguments` issue. A test in `runCLI` for flags before and after a stray argument.

### 2. Files that are not images become pages

**Class:** defect (internally inconsistent: the scanner already treats `.DS_Store`, `Thumbs.db` and `desktop.ini` as junk, but only at the top of the manga folder). **Priority:** High. **Effort:** M, with a decision.

**Where:** `internal/scanner/scanner.go:110-129` (`Pages` lists every file in a chapter folder) and `:176-193` (`PagesInArchive` lists every entry that is not a directory); `internal/grouper/grouper.go:156` keeps the file's extension.

**Evidence:**

```
M/Vol.01 Ch.001/{001.jpg 002.jpg 003.JPG Thumbs.db notes.txt ComicInfo.xml .hidden}
$ mangabind -input M -output o1
$ unzip -Z1 "o1/M - Vol.01.cbz"
c001/p0001.hidden  c001/p0002.jpg  c001/p0003.jpg  c001/p0004.JPG
c001/p0005.xml     c001/p0006.db   c001/p0007.txt              # 7 "pages", 4 are images

D/Vol.01 Ch.001/{.DS_Store 001.jpg 002.jpg}   ->   c001/p0001.DS_Store  c001/p0002.jpg  c001/p0003.jpg
```

A CBZ chapter made on macOS (`__MACOSX/._001.jpg`, `ComicInfo.xml`, `Thumbs.db`) gave 5 pages for 2 images. The JSON plan reports the inflated `page_count`, so a consumer shows the wrong number.

**Why it matters:** the README promises output "ready to hand off to Kindle Comic Converter, mangapress, or any other reader". macOS writes a `.DS_Store` into every folder Finder opens, and a name that starts with `.` sorts before `001`, so the junk file becomes the first page of the chapter. Downstream, mangapress 0.7.2 does skip such files (checked with a CBZ of two PNGs plus a `.DS_Store` and an `.xml`: it reported `skipped_non_images`, count 2, and wrote two pages), so the whole pipeline survives, but a plain reader opening the `.cbz` does not, and every count mangabind reports is off.

**Direction:** decide the rule, then use it in both `Pages` and `PagesInArchive`. An allow-list of image extensions (jpg, jpeg, png, gif, webp, avif, bmp, tif/tiff, jxl) is the safe default, with a `skipped` warning for the rest so that an unusual image extension is reported rather than dropped silently, the way unsupported files at the root already are. `__MACOSX/` entries and names starting with `._` are covered by the same list. **Decision for the owner:** allow-list plus warning, or only extend the existing junk deny-list.

### 3. A failed or interrupted write destroys the previous volume and leaves a partial file

**Class:** defect (clig.dev: be crash-only, exit cleanly on Ctrl-C and say so; ADR 0007: never leave the user unsure what happened). **Priority:** Medium (High if volumes take minutes to write). **Effort:** M.

**Where:** `internal/cbz/cbz.go:28-50`: `os.Create(outPath)` truncates the destination first; on error the code calls `zw.Close()`, which writes a central directory over whatever was copied, and returns. There is no temporary name, no rename, no cleanup, and no signal handling anywhere in `cmd/`.

**Evidence:**

```
# a good 480 MB volume exists; page 40 becomes unreadable; run again
$ mangabind -input Big -output oj
mangabind: writing volume 1: adding Big/Vol.01 Ch.001/40.jpg: open ...: permission denied
exit=1
$ ls -l oj/     ->   312 MB "Big - Vol.01.cbz"      # was 480 MB; well-formed zip with 39 pages

$ timeout -s INT 0.25 mangabind -input Big -output oi
$ unzip -Z1 "oi/Big - Vol.01.cbz"   ->   End-of-central-directory signature not found   # 98 MB, no message at all

$ ( ulimit -f 2000; mangabind -input F -output of )          # simulated full disk
mangabind: writing volume 1: adding ... 004.jpg: write ...: file too large     exit=1   # 2 MB partial file left
```

Also `defer f.Close()` (line 37) ignores the error of closing a file that was written, and `.golangci.yml` excludes `(*os.File).Close` from `errcheck` with a comment saying the important close is already checked; that is true for `zw.Close()` but not for `f.Close()`, which is where a delayed write error (network file systems, quotas) is reported.

**Why it matters:** re-running a conversion is the normal way to fix a mistake, and the failed re-run takes the good copy with it, leaving a file that looks finished: the interrupted case is not even a valid archive, and the page-40 case is a valid archive that is silently shorter. In the Ctrl-C case the person is told nothing.

**Direction:** write to `<name>.cbz.part` in the same folder, check `zw.Close()` and `f.Close()`, sync, rename onto the final name only on success, remove the partial file on every error path. Catch SIGINT/SIGTERM with `signal.NotifyContext`, stop between pages, remove the partial file, print one line (`interrupted; the partial file was removed`) and exit 130. Fix the `errcheck` comment.

### 4. One unusual archive entry ends the manga, `-dry-run` had promised success, and every page re-opens the archive

**Class:** defect (ADR 0011: the plan "executes the same plan"; protocol document: a plan reports what would be written). **Priority:** Medium. **Effort:** M.

**Where:** `internal/cbz/cbz.go:73-88` (`openPage`): each page of a source `.cbz` calls `zip.OpenReader` and then `archive.Open(name)`. `Reader.Open` follows `io/fs` rules, so a name that is not a valid `fs` path is refused, and it returns the *first* entry of that name, not the one the scanner listed.

**Evidence:**

```
Vol.03 Ch.003.cbz  holds  a.jpg  ../evil.jpg
$ mangabind -input M -output o2 -dry-run -json     ->   plan: 2 pages, "included", status completed
$ mangabind -input M -output o3
wrote o3/M - Vol.01.cbz (7 pages)
wrote o3/M - Vol.02.cbz (5 pages)
mangabind: writing volume 3: adding ...Vol.03 Ch.003.cbz: open ../evil.jpg: invalid argument     exit=1
```

Volumes 4 and 5 were never attempted (the loop returns at the first failed write, `main.go:600`), and `M - Vol.03.cbz` was left as an empty zip. Entries named `./rel.jpg` or `/abs.jpg` fail the same way. An archive with two entries both named `p1.jpg` ("1" and "dup-second") produced two pages that both contain "1": the second image was silently replaced by the first.

The cost of re-opening, measured on a chapter `.cbz` of *N* one-byte entries: 1,000 entries 1.5 s, 4,000 entries 25.5 s, 8,000 entries 111 s. The time grows with the square of the entry count, and `govulncheck` (finding 14) shows that the standard library's `Reader.Open` has had a quadratic-cost bug of its own (GO-2026-4342, `cbz.go:41` → `Reader.Open`), which this per-page call pattern multiplies.

**Why it matters:** a plan that promised success followed by a run that fails halfway is the exact case `-dry-run` exists to prevent, and the rest of the series is lost to one odd entry. The duplicate-name case is wrong output with exit 0, which is the worst kind.

**Direction:** open each source archive once per volume, keep the `*zip.File` the scanner listed and call `File.Open()` on it (no name lookup, so no `fs.ValidPath` rule and no first-match surprise), and treat entries with `..`, a leading `/` or a drive prefix as skipped-with-warning at scan time, so the plan and the run agree. Keep going to the next volume after a failed one, as `-batch` already does across manga.

### 5. The default output folder lands inside the input for `Manga/`, `.` and `..`

**Class:** defect (README: "never inside `--input` itself, since that would make the next run see the output folder as a bogus chapter"). **Priority:** Medium. **Effort:** S.

**Where:** `cmd/mangabind/main.go:230-232`: `filepath.Join(filepath.Dir(input), filepath.Base(input)+" (mangabind)")` on the path as typed.

**Evidence:**

```
$ mangabind -input Manga/ -dry-run        # trailing slash, what tab completion produces
mangabind: no -output given, writing to Manga/Manga (mangabind)
$ cd Manga && mangabind -input .          # real run
$ ls -A       ->   ". (mangabind)"  and inside it  ". - Vol.01.cbz"  ". - Vol.02.cbz"
$ mangabind -input ..   ->   ".. (mangabind)/.. - Vol.01.cbz"
```

The `.` case writes files whose names start with a dot, so they are hidden in most file managers. A second run over `Manga/` then reports `"Manga (mangabind)"` as an unparsed chapter folder, which is the failure the README says the design avoids.

**Direction:** `filepath.Abs` then `Clean` before deriving the folder and the file names (`Base` of the absolute path is the real folder name, and `Dir` its real parent), so the default is the same sibling folder however the path was typed.

### 6. A decompression bomb is copied out in full

**Class:** gap (ADR 0014 sets the threat model: a manga folder from someone else; nothing there or in ADR 0007 limits what a `.cbz` chapter may expand to). **Priority:** Low to Medium. **Effort:** M, with a decision.

**Evidence:** a 407,791-byte `.cbz` whose single entry is 400 MiB of zeros became a 419,430,542-byte volume in 1.05 s (about 1,000:1), with no warning. `io.Copy` in `cbz.go:67` has no limit, and volumes are written with `zip.Store`, so the expansion is kept on disk. Because every page is written from its source, a hostile download can fill a disk.

**Direction:** compare each entry's `UncompressedSize64` against its `CompressedSize64` and an absolute ceiling at scan time and skip, with a warning, an entry that no page of a comic can be (for example above 256 MiB, or a ratio above 1,000:1 with a size above 16 MiB). **Decision for the owner:** whether mangabind should defend against this at all, or leave it to the user's choice of sources; either answer is fine, but it should be written down, because ADR 0014 already chose to defend against the link variant.

### 7. The metadata file can crash the program or produce nonsense volume numbers

**Class:** defect (ADR 0010 describes a validated file; `internal/metadata` rejects other malformed values with a message). **Priority:** Low. **Effort:** S.

**Where:** `internal/metadata/metadata.go:107-112` (`make([]chapterKey, 0, hi-lo+1)`) and `:76` (`strconv.ParseFloat` accepts `NaN`, `Inf`, negatives).

**Evidence:**

```
{"schema_version":1,"volumes":[{"number":"1","chapters":["1-9000000000"]}]}
$ ( ulimit -v 4000000; mangabind -input MM -output omm )
runtime: out of memory: cannot allocate 216002461696-byte block      fatal error: out of memory   (Go stack dump, exit 2)

"number":"NaN"  ->  wrote omm_NaN/MM - Vol.NaN.cbz (0 pages)         # an empty volume, written
"number":"Inf"  ->  MM - Vol.-9223372036854775808.cbz                 # int(Inf) in VolumeFileName
"number":"-3"   ->  MM - Vol.-3.cbz
```

A chapter listed under two volumes is also taken silently, the last one winning (`:86`). Exit 2 from a Go runtime crash also collides with "usage error".

**Direction:** reject volume numbers that are not finite or are negative, cap a range (or expand it lazily), warn on a chapter listed twice. The file is written by hand or by mangabound, so this is robustness, not an attack.

### 8. `-json=true` is not recognised when the flags fail to parse

**Class:** defect (ADR 0011: "when machine mode was requested, a non-zero exit still produces a parseable report on stdout whenever the process can do so"). **Priority:** Low. **Effort:** S.

**Where:** `cmd/mangabind/main.go:139-146`: `hasFlag` compares each argument to `-json` or `--json` exactly.

**Evidence:** `mangabind -json -bogus` prints a JSON report with `invalid_arguments`; `mangabind -json=true -bogus` prints the human error and no JSON. (`-json=true` on a valid command line works, because `flag` handles the `=`.) mangabound passes plain `--json`, so the app is not affected.

**Direction:** accept `-json=…` and `--json=…` (parse the boolean), or run the pre-scan with a throwaway `flag.FlagSet` that ignores unknown flags.

### 9. Links to folders: the README promises a warning, and the code gives a different one

**Class:** defect (documentation against code). **Priority:** Low. **Effort:** S.

**Evidence:** the README says a link "that leads to a folder is left out and reported as a `link_skipped` warning". A symbolic link to a chapter folder inside the input (`Vol.02 Ch.002 -> real/Vol.02 Ch.002`) is reported as `unsupported_input_file`, "found unrecognized file, skipped", because `os.ReadDir`'s `IsDir()` is false for a link and `Scan` falls through to the unsupported-file branch (`scanner.go:61-83`). In `-batch`, a link to a manga folder in the library is skipped with no message at all in either mode (`main.go:251` and `protocol.go:281`, both `IsDir()` on the directory entry), which hides that a manga was not processed.

**Direction:** classify a symbolic link before the file-type checks, with the same `link_skipped` code and the reasons of ADR 0014, in `Scan` and in both batch loops.

### 10. The batch summary under-counts a manga that failed after writing some volumes

**Class:** defect. **Priority:** Low. **Effort:** S.

**Evidence:** a library of four folders with one manga failing on its second volume ended with `mangabind: processed 4 manga, 2 volume(s), 2 page(s) total`; three volumes had been written. `runBatchWithOutput` (`main.go:261-278`) does `continue` on error before adding the summary, so the volumes a failed manga did write are not counted. The machine report is right (`addManga` takes the partial summary).

## Findings — conformance with clig.dev

ADR 0009 adopted `--version`, real help, `-i`/`-o`, `--dry-run`, `--quiet` and `--batch`, and declined color, a configuration file, environment variables, man pages and completions; ADR 0011 and 0013 later added the JSON report and progress. The items below are clig.dev points that none of those records addresses.

### 11. Help goes to stderr, and a usage error prints the whole help

**Class:** gap. **Priority:** Medium. **Effort:** S.

**Where:** `cmd/mangabind/main.go:182` (`fs.SetOutput(output)`, the error stream) and `:200` (`fs.Usage`).

**Evidence:** `mangabind -h` and `--help` exit 0 and write the 44-line help to stderr, so `mangabind -h | less` shows nothing and `mangabind -h 2>/dev/null` shows nothing. An unknown flag prints Go's one-line message and then the same 44 lines. A stray positional argument with no `-input` prints only the usage and no message naming the argument. clig.dev asks for help on stdout when it is requested, a short message plus a pointer to `-h` when the input is wrong, and a suggestion when the user's meaning can be guessed (`-inupt` → `-input`).

**Direction:** when help was requested (`ErrHelp`), print to stdout; on a usage error print the error, one line with the synopsis and `Try 'mangabind -h' for the full list`. **Decision for the owner:** whether to add a one-edit-distance "did you mean" suggestion, which is a few lines.

### 12. Informational lines on stdout, and an empty input exits 0

**Class:** gap, and one *reconsider* (ADR 0007 decided the empty-input message, not the exit code). **Priority:** Low. **Effort:** S.

**Evidence:** `no -output given, writing to …` (`main.go:107`), `using metadata file …` (`:340`) and `no chapter folders or .cbz files found in …` (`:358`) are written to stdout, next to the `wrote …` lines that are the command's result, so `mangabind -input x | tee list.txt` captures them. An empty folder exits 0. For a person that is a message and a success; for a script it is "worked, produced nothing". The JSON report already says it (`no_chapters_found`, status `completed_with_warnings`).

**Direction:** send the three notices to stderr; leave the exit code as it is, and say in the README that a run that found nothing exits 0 with a warning. If the owner prefers a non-zero code, that is a protocol-visible change and needs an ADR.

### 13. Exit codes and streams are not written down where a user looks

**Class:** gap. **Priority:** Low. **Effort:** S.

**Evidence:** exit codes 0, 1 and 2 appear only in ADR 0011; neither the README nor `-h` mentions them. The help examples are all Windows paths (`D:\Manga\…`) although the installer, the release and the CI cover macOS and Linux. `-n` and `-q` are listed as separate entries from `-dry-run` and `-quiet` rather than together. The README says `--input`, the help says `-input`; both work, but one should be chosen for documentation (clig.dev's own examples use the double dash for long names).

**Direction:** a short "Exit codes" and "Output streams" section in the README, one POSIX example in the help, and one spelling in the docs.

## Findings — supply chain and release

### 14. The release toolchain is out of support, and one of its open vulnerabilities is reachable

**Class:** gap (ADR 0008 chose simple binary releases; nothing says how the toolchain is kept current). **Priority:** Medium. **Effort:** S.

**Where:** `go.mod` (`go 1.23`), `ci.yml` and `release.yml` (`go-version: "1.23"`), CONTRIBUTING ("Requires Go 1.23+").

**Evidence:** `go version -m` on the published `mangabind_linux_amd64` of `v0.6.1` says `go1.23.12`, the last release of a line that no longer gets fixes. `govulncheck` in source mode under Go 1.23.12 reports two vulnerabilities in the call graph: GO-2026-4342 (`archive/zip` builds its index with excessive CPU; fixed in Go 1.24.12; reached from `cbz.go` → `Reader.Open`, on input the program reads from the person's downloads) and GO-2026-4602 (`os`, FileInfo escaping from an `os.Root`; mangabind does not use `os.Root`, so it is not exploitable). Binary mode on the *published* archive reports 45, which is an over-count: the release is built with `-s -w`, which strips the symbols govulncheck needs, so it falls back to listing every vulnerability of that Go version. An unstripped build with the same toolchain reports the same two as source mode.

**Direction:** move `go.mod`, the workflows and CONTRIBUTING to a supported Go (1.26 or newer), with `go-version-file: go.mod` so there is one place to change; add `govulncheck ./...` to CI.

### 15. CI and release hygiene

**Class:** gap. **Priority:** Medium (the first three items) to Low. **Effort:** S each, M together.

| Item | What was found |
|---|---|
| Release is not gated on CI | `release.yml` runs on any `v*` tag with `contents: write` and does not depend on a passing CI run for that commit. |
| Branch protection | `GET /branches/main/protection` returns 404: no required checks, no restriction on force pushes. |
| Actions are tags, not commits | `actions/checkout@v4`, `actions/setup-go@v5`, `golangci/golangci-lint-action@v7`, `goreleaser/goreleaser-action@v6`. |
| Tools float | `golangci-lint` and `goreleaser` both `version: latest`, so a new lint or a new goreleaser can break a release or a PR with no change in the repository. |
| Missing checks | no `-race`, no coverage report or threshold, no `govulncheck`, no `go mod tidy` diff check (the goreleaser hook runs `go mod tidy` at release time only). |
| No update automation | no `dependabot.yml` (the Actions and the Go toolchain are what would be updated), Dependabot security updates are disabled, no `SECURITY.md`, no way to report a vulnerability privately other than guessing. |
| Release artefacts | checksums are published but unsigned and in the same place as the binaries, so they do not defend against a compromised release; no `-trimpath`, no SBOM, no build provenance attestation. |
| Installers | `install.sh` and `install.ps1` always fetch the latest release, never check `checksums.txt`, and cannot install a given version; `install.sh` finds the tag by `grep` on the API's JSON; `install.ps1` writes a fixed temp name and overwrites the install folder with `-Force`. mangabound verifies checksums itself, but a person using `curl … | sh` gets none. |

**Direction:** one pull request for the workflow changes (pin by commit SHA with a comment of the tag, pin tool versions, add `-race`, `govulncheck`, a tidy check, `needs:` or a tag-on-green rule for the release), one for `dependabot.yml` and `SECURITY.md`, one for the installers (verify the SHA-256 from `checksums.txt`, accept a version argument). Branch protection is a setting, not a pull request. **Decision for the owner:** signing and provenance (`actions/attest-build-provenance` is free on public repositories) are worth doing only if people other than the owner and mangabound install this.

## Findings — documentation and tests

### 16. Documents that disagree with each other or with the code

**Class:** defect (documentation). **Priority:** Low. **Effort:** S.

- ADR 0009's own file says `Accepted`, while the index in `docs/adr/README.md` strikes it through as "superseded by 0011". ADR 0011 says "supersedes ADR 0009" and, in the next paragraph, that "the other conclusions in ADR 0009 remain sound", which are the flags the program still follows. It is superseded *in part*; the status line of 0009 should say `Partly superseded by 0011` and the index should not strike it through.
- `docs/machine-protocol-v1.md` shows `"tool_version": "0.6.0"` in the handshake example; the current release is 0.6.1. Harmless, but a consumer copying the example into a test fixture will fail a version check.
- The README's "never inside `--input`" (finding 5) and its description of links to folders (finding 9) are not what the program does.
- The README's `Status` section says "Early development" for a program with a versioned protocol and seven published releases; either is fine, but the machine contract is the part other software depends on.

### 17. The tests do not reach the layer where most of these findings live

**Class:** gap. **Priority:** Medium. **Effort:** M.

**Evidence:** per-function coverage of `cmd/mangabind`: `main` 0.0%, `runCLI` 45.5%, `protocol.go addIssue` 57.1%, `runBatchWithOutput` 70.8%, `processMangaDetailed` 74.5%, `runMachine` 75.0%. Findings 1, 5, 8, 11 and 12 are all in argument handling and its first lines; the packages below it (`grouper`, `metadata`, `scanner`, `cbz`) are at 90 to 98%. There is no test of the order of flags, of a path with a trailing slash or a dot, of a write that fails halfway, or of a `.cbz` with an entry the standard library cannot open. CI does not measure coverage, so the gap is not visible.

**Direction:** each fix above ships with its test in `runCLI` (which already takes `args, stdout, stderr`, so the tests need no process), and the CI job prints the coverage so the number is seen.

## What changes for mangabound

mangabound passes only flags, absolute paths, `--json` and (for dry runs) `--dry-run`, so it is not exposed to findings 1, 5, 8, 11, 12 and 13. It *is* exposed to finding 2 (the page count it shows is the count of files, not of images; the extra files reach mangapress, which skips them with a `skipped_non_images` warning, so the books are right but the counts are not, and the warning will appear in mangabound's results for every such book), to finding 4 (a plan that said "included" and a run that failed), and to findings 3, 6 and 7 in ways that depend on where mangabound runs mangabind (it uses a temporary workspace, which would hold the partial file; this was not checked here and belongs to the mangabound side of the audit). Nothing in this report changes mangabound's pin until a mangabind release exists; any fix must stand on its own for someone using the command line alone.
