# 10. Resolve missing volume numbers from a local metadata file, not a network provider

Date: 2026-09-13

## Status

Accepted

## Context

Mangabind can only group chapters into volumes when the volume number is already present in the
chapter's own name (`Vol.01 Ch.0001 - ...`, `Volume 1 Chapter 5`, ...). A real, demonstrated
limitation follows from that: a manga whose chapters are only ever named `Chapter 1`, `Chapter 2`,
... `Chapter 150` (no volume information anywhere) currently produces **zero volumes** -
`ChapterOnlyParser` and `BareNumberParser` never set `Volume`, so every one of those chapters lands
in `Unassigned` and nothing gets written. This is the opposite of Mangabind's whole point.

A proposal was raised to fix this by resolving the missing `chapter -> volume` mapping from an
external source, using an external metadata API endpoint as a first example, with a
`MetadataProvider` interface designed to support other sources later.

Investigating this against an actual metadata API (fetched live, not just documentation) confirmed
it's technically workable: public endpoints with rate limits
and structured schemas can map
chapters to volumes for well-catalogued series. But two things argue against building this into
Mangabind:

1. **A local, hand-authored (or externally-generated by any means) metadata file already fully
   solves the stated problem**, with none of a network provider's costs: no HTTP client, no
   third-party ToS to comply with (external APIs often require crediting sources,
   honoring removal requests, no ads/paid access), no rate limits, and - the hardest part of the
   original proposal - no "which manga is this folder, actually" identification problem, since the
   user already knows what manga they're organizing. The network provider is convenience layered on
   top of an already-complete solution, not new capability.
2. **Resolving the mapping and *acquiring* the mapping are different responsibilities.** Mangabind
   organizes structure from information it's given (see ADR 0003, ADR 0005, ADR 0007 - it has never
   reached out to the network to get information it doesn't have locally). Talking to an external
   metadata API is outside what Mangabind does. Baking a provider
   abstraction into Mangabind for a single call site, before a second real provider exists, is also
   premature abstraction on top of a premature scope expansion.

## Decision

Mangabind gained a local chapter-to-volume metadata mechanism only - no network code anywhere in
the project:

- A new `internal/metadata` package defines the on-disk schema (`schema_version`, `manga.title`
  informational, `volumes: [{number, chapters}]`, `source` informational) and loads it into a
  `Map` with a `Lookup(chapter, special) (volume, ok)` method. `chapters` entries accept either a
  single token (`"8"`, `"8.5"`, `"21x1"`) or an inclusive integer range (`"1-7"`), since hand-typing
  150 individual chapter numbers defeats the point.
- `cmd/mangabind` looks for this file two ways: an explicit `-metadata-file` flag, or - the default,
  and the only option in `-batch` mode - a `mangabind.json` file living inside the manga's own input
  folder. `-metadata-file` and `-batch` are mutually exclusive (one file can't sensibly apply to
  every manga in a library; each manga folder gets its own convention file instead).
- Resolution policy: the chapter's own name always wins when it already has a volume. Metadata only
  fills chapters where the name provided none. If both are present and disagree, that's a warning
  (matching the existing `Conflict`/`Gap` reporting style) - never a silent override.
- No `MetadataProvider` interface, no external API client, no manga/work identification, no caching, no
  `-metadata-base-url`. If a network-driven source is ever wanted, it produces this same local file
  format (from outside Mangabind's binary - a separate script, or the planned future GUI, which is
  also the natural place to handle the identification/disambiguation problem visually) rather than
  Mangabind acquiring the data itself.

## Consequences

The chapter-number-only case is fixed for anyone willing to write (or generate) a small JSON file
once per manga. `parser.ChapterNameParser` and `grouper.Group` are both unchanged - the new package
plugs in entirely inside `cmd/mangabind`, between parsing a chapter's name and handing it to the
grouper, preserving the isolation ADR 0003 built between naming-convention detection and everything
downstream. Mangabind stays offline and dependency-free (ADR 0002, ADR 0007). If a real second
metadata source ever shows up, introducing a provider abstraction then - with two real
implementations to design against instead of one imagined one - will be a better-informed decision
than making it now.
